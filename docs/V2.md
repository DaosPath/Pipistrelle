# Pipistrelle V2 — 2.1.2.3

V2 is developed on the `v2` branch. V1 is frozen at tag `v1.0.0.0`.

## Version policy

Public Pipistrelle releases use four numeric components: `MAJOR.MINOR.PATCH.BUILD` (for example `2.0.0.0`). Cargo requires a three-component SemVer core, so `Cargo.toml` uses `2.0.0` while the canonical Pipistrelle release version lives in `VERSION` and is embedded into the binary at build time.

## Cryptography profiles

All secure MQTT traffic uses TLS 1.3. `PIPISTRELLE_TLS_PROFILE` accepts:

- `hybrid` (default): X25519MLKEM768 first, then X25519, P-256 and P-384 for compatibility.
- `pqc-strict`: only X25519MLKEM768 is accepted; non-PQC clients fail the TLS handshake.
- `classical`: X25519/P-256/P-384 only, intended for compatibility testing and PQC overhead comparisons.

The outbound bridge has an independent `PIPISTRELLE_BRIDGE_TLS_PROFILE`.

## Observability

The metrics port now exposes:

- `/metrics` — Prometheus metrics plus build, TLS negotiation and bounded outbound-queue/backpressure counters.
- `/health` — minimal liveness response.
- `/info` — version, MQTT/TLS version, active TLS profile and per-client outbound queue capacity.

## Benchmarking

`src/bin/pipistrelle-bench.rs` is the primary high-throughput load generator. It speaks MQTT v5 directly over Tokio TCP/rustls without Paho or Python. `loopback` validates full broker routing; `ingest` measures publish intake and uses a trailing QoS 1 marker for QoS 0 runs so completion cannot be mistaken for merely filling the client socket. The older `tools/benchmark.py` remains useful as an independent integration cross-check.

Native examples:

```bash
# End-to-end TCP routing
cargo run --release --bin pipistrelle-bench -- --mode loopback --clients 10 --messages 100000 --qos 0

# Raw ingest ceiling
cargo run --release --bin pipistrelle-bench -- --mode ingest --clients 10 --messages 100000 --qos 0

# Hybrid PQC TLS 1.3
cargo run --release --bin pipistrelle-bench -- --tls --tls-profile hybrid --ca config/cert.pem --mode loopback --clients 10 --messages 10000
```

The Python matrix is still available for an implementation-independent cross-check:

```bash
./scripts/bench-orange-pi.sh
```

Results are written to `bench-results/` and are intentionally not committed.

## Bounded outbound queues and backpressure

Starting with `2.0.0.1`, every connected MQTT client has a bounded outbound Tokio queue. `PIPISTRELLE_CLIENT_QUEUE_CAPACITY` controls the number of queued MQTT packets per client and defaults to `1024` (accepted range `16..65536`). The fast path uses `try_send`; when the queue is full, the publishing task awaits capacity, propagating pressure back toward the publisher instead of allocating memory without a bound.

Prometheus exposes:

- `pipistrelle_client_outbound_queue_messages`
- `pipistrelle_client_outbound_queue_capacity_messages`
- `pipistrelle_client_queue_backpressure_total`
- `pipistrelle_client_queue_backpressure_wait_seconds_total`

No messages are intentionally dropped by this mechanism. A slow consumer can reduce publisher throughput once its queue reaches capacity; that trade-off is deliberate and is safer than unlimited buffering.


## V2 2.0.0.2 resource isolation and latency

`2.0.0.2` extends the bounded-client work with explicit slow-consumer handling, per-client subscription quotas, a bounded remote bridge queue, and low-overhead routing latency telemetry.

Runtime controls:

- `PIPISTRELLE_MAX_SUBSCRIPTIONS_PER_CLIENT=256` — rejects additional new filters with MQTT v5 SUBACK reason `0x97` (Quota exceeded). Re-subscribing an existing filter does not consume another slot.
- `PIPISTRELLE_SLOW_CONSUMER_POLICY=backpressure|disconnect` — `backpressure` remains the safe default. `disconnect` removes a client whose full outbound queue does not recover within `PIPISTRELLE_SLOW_CONSUMER_TIMEOUT_MS` (default `5000`).
- `PIPISTRELLE_BRIDGE_QUEUE_CAPACITY=4096` — bounds memory used while the remote bridge is slow or unavailable.
- `PIPISTRELLE_BRIDGE_QUEUE_POLICY=drop-newest|backpressure` — default `drop-newest` isolates the local broker from a failed remote QoS 0 bridge; drops are explicit and counted.
- `PIPISTRELLE_LATENCY_SAMPLE_RATE=64` — records one routing-latency observation per 64 publishes. The effective rate is normalized to a power of two so sampling uses a bit mask rather than integer division in the publish hot path.

The bridge queue only receives topics matching its configured local bridge prefix (`sensor/` in the current bridge implementation), so unrelated MQTT traffic does not fill or wait on the remote bridge queue.

Prometheus now exposes slow-consumer disconnects, subscription-quota rejections, bridge queue depth/capacity/drop/backpressure counters, current tracked subscriptions, a sampled route-latency histogram, and approximate p50/p95/p99 gauges.


## V2 2.0.0.3 — 20M/s ingest target

`2.0.0.3` is a publish hot-path optimization release. The target was at least **20 million MQTT v5 PUBLISH messages/s** on the Orange Pi native benchmark without weakening authentication, TLS, or the bounded-memory work from earlier V2 releases.

The optimized fast path applies only when all of these conditions are true:

- MQTT QoS 0 PUBLISH.
- `retain=false`.
- The authenticated session has a cached global write ACL (`#`).
- There are currently no active subscriptions.
- The remote bridge is disabled.

All other traffic continues through the full authorization/routing/backpressure path.

Hot-path changes:

- ACL topic matching is allocation-free; exact filters and `#` have dedicated constant/near-constant fast paths.
- Sessions cache unconditional global read/write ACL capabilities after authentication, avoiding a username hash lookup and ACL traversal per PUBLISH for common service/admin accounts.
- The router maintains an exact atomic count of active routes; zero-routing ingest bypasses the router lock and route-result allocations, and automatically re-enters the fast path after subscriptions are removed.
- Publish counters are per-session rather than one globally contended atomic cache line. Prometheus aggregates active counters plus retired-session totals at scrape time.
- The zero-routing QoS 0 path executes synchronously in the decode loop, bypassing unnecessary async dispatch.

The full routing path remains bounded and preserves the `2.0.0.1/2.0.0.2` slow-consumer protections.


## V2 2.0.0.4 — 2M/s end-to-end routing target

`2.0.0.4` targets sustained end-to-end QoS 0 delivery rather than raw ingest. The release keeps authentication, ACLs, bounded client queues, slow-consumer backpressure, bridge isolation and TLS/PQC enabled; the throughput gain does not come from disabling those protections.

Routing/output changes:

- Exact non-shared subscriptions maintain a copy-on-write `topic -> Arc<[SubscriptionInfo]>` cache. When all active routes are exact, publishes avoid Trie traversal, topic-level `Vec` allocation and per-message subscription metadata cloning. Wildcards and shared subscriptions automatically force the full Trie path.
- QoS 0 outbound PUBLISH serialization computes Remaining Length up front and writes directly into one final `Vec`, avoiding the generic encoder's intermediate payload allocation. A unit test verifies byte-for-byte equivalence with the generic encoder.
- Client writer tasks preserve the bounded queue and message order but coalesce already-queued MQTT packets into larger writes. Defaults are `PIPISTRELLE_WRITER_BATCH_PACKETS=256` and `PIPISTRELLE_WRITER_BATCH_BYTES=262144`. Light traffic is still written immediately; batching only drains packets that are already queued.
- The native benchmark reader now uses a reusable `BytesMut` and parses multiple MQTT packets per socket read, eliminating a measurement bottleneck caused by per-packet allocations and `read_exact` calls. This benchmark optimization is separated from broker A/B measurements.

The writer batch settings are exposed in `/info` and as Prometheus gauges. Backpressure remains controlled by `PIPISTRELLE_CLIENT_QUEUE_CAPACITY`; batching does not make the queue unbounded.


## V2 2.1.0.0 — MQTT protocol and persistent-state milestone

`2.1.0.0` is the first V2 feature release after the throughput-focused `2.0.0.x` series. It expands MQTT v5 behavior without removing authentication, PQC TLS, bounded queues or the existing fast paths.

### QoS 2

- Inbound QoS 2 implements `PUBLISH → PUBREC → PUBREL → PUBCOMP`; the Application Message is routed only after `PUBREL`.
- Duplicate QoS 2 PUBLISH packets reuse the pending Packet Identifier and are acknowledged without routing twice. A repeated PUBREL after completion returns `0x92` and does not redeliver the Application Message.
- Outbound QoS 2 tracks `AwaitPubRec` and `AwaitPubComp`. Persistent Sessions store both phases in SQLite and resume with `DUP=1 PUBLISH` or `PUBREL` as appropriate.
- Persistent inbound state is committed before PUBREC and outbound phase transitions before continuing the handshake, reducing ACK-vs-storage races.

### Retained messages and subscription behavior

- `RETAIN=1` stores/replaces retained state in SQLite; zero-length retained publishes delete it.
- New subscriptions replay matching retained messages with `RETAIN=1` and QoS capped by the granted subscription QoS.
- MQTT v5 Retain Handling `0/1/2`, Retain As Published, No Local, Subscription Identifier, and subscription-option persistence are implemented. Shared subscriptions reject No Local and do not receive retained replay on creation.

### Last Will and Testament

- CONNECT decodes Will QoS, retain, topic, payload and MQTT v5 Will properties including Will Delay.
- Runtime Will delivery honors normal `DISCONNECT 0x00` suppression, abrupt disconnect/keep-alive loss, retained Will storage, Will Delay, and cancellation when the same persistent Session reconnects before the delay expires.
- ClientID takeover publishes or suppresses the previous connection's Will according to Clean Start, Session Expiry and Will Delay semantics.

### Persistent Sessions and takeover

- CONNACK reports `Session Present` when `Clean Start=0` successfully resumes stored Session state.
- Persistent subscriptions and offline QoS 1/2 state survive disconnects and broker restarts. Session Expiry countdowns are reconstructed after restart rather than resetting indefinitely.
- The sessions table tracks online/offline state and the last close time. Registration is persisted before CONNACK to avoid a fast-disconnect race.
- A second connection with the same ClientID atomically becomes the current owner, while the old connection receives MQTT v5 `DISCONNECT 0x8E (Session taken over)`. Old connection cleanup cannot erase its replacement.
- Persistent Session state is additionally bound to the authenticated principal used by Pipistrelle ACLs. A different valid user attempting to resume or erase the same ClientID is rejected with CONNACK `0x87 (Not Authorized)`; the legitimate owner remains connected. This binding is restored from SQLite after broker restart.

### Protocol tests

`test_protocol_v2.py` uses raw MQTT v5 control packets over TCP. It checks retained store/replay/delete, Retain Handling/RAP/No Local, QoS 2 exactly-once sequencing, outbound QoS2 resume from PUBREL, immediate/delayed/retained Will behavior, `Session Present`, and repeated ClientID takeover. Additional restart gates verify retained, offline QoS1, inbound/outbound QoS2 and Session Expiry across a full broker restart.

## V2 2.1.1.0 — PUBLISH properties, Message Expiry and crash-safe Will state

`2.1.1.0` closes the two compliance gaps explicitly left by `2.1.0.0`: Application Message properties are now carried through the broker instead of being dropped, and Last Will state is durable across an abrupt broker process failure.

### Application Message properties

Pipistrelle converts incoming PUBLISH/Will properties into an owned internal representation so they can outlive the network decode buffer and be stored in SQLite. Routing and retry paths preserve:

- Payload Format Indicator.
- Message Expiry Interval.
- Content Type.
- Response Topic.
- Correlation Data.
- User Properties, including duplicate keys and their original order.

Subscription Identifiers remain delivery metadata generated from the subscriber's subscriptions; a Client->Server PUBLISH containing one is rejected as a Protocol Error. Since `2.1.2.1`, Topic Alias is accepted Client→Server with a configurable CONNACK maximum, mapping/update/reuse semantics and connection-local reset. Since `2.1.2.2`, CONNECT Topic Alias Maximum is also honored for Server→Client QoS0 delivery: the first outbound PUBLISH establishes the mapping with Topic Name + alias and subsequent PUBLISH packets may reuse the alias with a zero-length Topic Name. Alias state remains connection-local in both directions.

### Message Expiry

The broker records a wall-clock start time when an Application Message carrying Message Expiry enters the Server. Forwarded PUBLISH packets expose the remaining interval after subtracting time spent waiting. Copies which expire before onward delivery begins are removed from offline QoS state or retained storage. Once a QoS1/QoS2 delivery has begun, its handshake/retry state is allowed to finish rather than being silently abandoned.

Retained messages, offline QoS1, inbound QoS2 and outbound QoS2 persist the owned properties as JSON beside their existing SQLite state, with migrations for databases created by earlier V2 releases.

### Crash-safe Last Will

A connection's Will is stored in SQLite before CONNACK. The row contains owner principal, topic, payload, QoS, retain, Will Delay, Application Message properties, Session Expiry and—once the connection is lost—the durable publication deadline.

- `DISCONNECT 0x00` deletes the stored Will.
- Abrupt disconnect arms and persists the Will Delay deadline before the timer runs.
- `SIGKILL`/server failure restores the Will on restart. OASIS permits Will publication to be deferred until a subsequent server restart.
- A reconnect that continues the same Session before Will Delay expires cancels both the timer and persisted row.
- ClientID takeover with `Clean Start=0` and a delayed Will suppresses the exiting connection's Will and deletes its persisted copy, preventing stale Will resurrection after a later restart.
- Will Message Expiry starts when the Will is actually published, not while Will Delay is counting.

`pipistrelle_pending_wills_current` exposes the number of persisted/armed Wills currently represented by the runtime. `/info` advertises `publish_application_properties`, `message_expiry`, and `will_crash_persistence`.

### Tests and performance gate

The raw socket suite now has 18 MQTT v5 protocol scenarios. The destructive restart suite has 8 scenarios and repeatedly uses container `SIGKILL` to validate active/delayed/cancelled/takeover Wills plus retained, offline QoS1 and both QoS2 directions across restart.

On the Orange Pi release candidate with 128-byte payloads:

- 50M TCP QoS0 ingest: **20.134 M msg/s**, 0 failures.
- 50M TCP QoS0 end-to-end loopback: **2.709 M msg/s**, 0 failures, about **122.4 MiB** broker memory after the run.

The zero-route ingest fast path still validates protocol-sensitive fields but avoids constructing owned Application Properties when no forwarding or persistence is required.

### Current compliance boundary

`2.1.1.0` fixes the PUBLISH/Will property and crash-persistence gaps from `2.1.0.0`, but Pipistrelle still deliberately does **not** claim complete MQTT v5 conformance. The canonical status is maintained in [`MQTT5_COMPLIANCE.md`](MQTT5_COMPLIANCE.md). Remaining work includes control-packet families and negotiated limits that are independent from the Application Message path fixed here.


## V2 2.1.2.1 — 200M optimized ingest ceiling + MQTT 5 Topic Alias inbound

`2.1.2.1` is an interim build on the `2.1.2.x` line; it does **not** consume the `2.1.3.0` roadmap milestone, which remains reserved for Enhanced AUTH/fuzzing/compliance hardening.

### Topic Alias Client→Server

- CONNACK advertises `PIPISTRELLE_TOPIC_ALIAS_MAXIMUM` (default `32`; `0` disables inbound aliases).
- A non-empty Topic Name + Topic Alias establishes or updates the mapping for that Network Connection.
- A zero-length Topic Name + established alias resolves the mapped topic. Alias `0` or above the negotiated maximum yields `0x94`; an unmapped in-range alias with empty Topic Name yields Protocol Error `0x82`.
- Alias state is intentionally **not** persistent Session state: reconnecting clears mappings even when `Session Present=1`.
- Topic Alias is connection-local metadata and is never blindly forwarded between connections. `2.1.2.2` can independently assign a Server→Client alias when the receiving client advertises a non-zero Topic Alias Maximum.

### ARM64 ingest path and benchmark engine

The zero-route QoS0 scanner keeps the full MQTT codec as fallback, but caches validated packet layout and compares hot headers in batches. A routing mutation epoch prevents a concurrent SUBSCRIBE/UNSUBSCRIBE from being skipped by a batch that began while the router was empty. Topic-Alias traffic uses a separate validated layout only after the connection has established the alias through the general MQTT path.

For the 9-byte steady Topic-Alias structural prefix, AArch64 uses a 16-frame `u64 + u8` matcher. It still validates every frame's fixed header, Remaining Length, zero-length Topic Name, property length/id and alias bytes. A regression test feeds 16 different payloads through this path and verifies they are all accepted, then changes one alias byte and verifies the batch stops exactly before the changed frame.

The benchmark keeps the portable Tokio engine and adds Linux-only `--sendfile` for plain-TCP QoS0 ingest. It still performs CONNECT/CONNACK validation, validates Topic Alias Maximum, sends the first counted full-topic mapping PUBLISH normally, transmits the repeated MQTT window from an independent `memfd` per publisher using `sendfile()`, and ends with an ordered QoS1 marker whose PUBACK is mandatory. The engine reports itself as `rust-native-sendfile`; it changes load-generation overhead, not the MQTT bytes accepted by the broker.

## V2 2.1.2.2 — bidirectional Topic Alias fast-route

`2.1.2.2` extends the connection-local Topic Alias machinery through the complete QoS0 routing path. A subscriber that advertises CONNECT Topic Alias Maximum can now receive Server→Client aliases. The first delivery for a topic establishes `Topic Name + Topic Alias`; later deliveries may carry a zero-length Topic Name and the established alias. If the publisher remaps an inbound alias to another topic, `topic_alias_epoch` invalidates the hot cache before the next exact-route lookup.

The optimized exact-route path preserves the normal bounded outbound queue and falls back to the general MQTT codec whenever its assumptions do not hold. When inbound and outbound alias numbers match, steady-state packets can pass through as wire-ready blocks; when they differ, only the alias bytes are rewritten; when the subscriber does not accept aliases, the path expands the packet back to a full Topic Name.

## V2 2.1.2.0 — MQTT flow control, UNSUBSCRIBE and stricter wire compliance

`2.1.2.0` is an incremental MQTT v5 compliance release. It deliberately keeps the V2 standalone architecture and QoS0 fast paths while closing several negotiated-control gaps that were still marked partial in `2.1.1.0`.

### UNSUBSCRIBE / UNSUBACK

- MQTT v5 `UNSUBSCRIBE` (`0xA2`) and `UNSUBACK` (`0xB0`) are first-class codec packets.
- Per-filter reason codes preserve request order: `0x00` when a subscription is removed and `0x11` when no subscription existed.
- Topic Filter wildcard/shared-subscription syntax is validated before mutation.
- Persistent deletion is committed to SQLite **before** UNSUBACK, so ACK followed immediately by `SIGKILL` cannot resurrect a removed subscription.

### Receive Maximum

- `PIPISTRELLE_RECEIVE_MAXIMUM` defaults to `1024` and is advertised in CONNACK.
- Client -> Server QoS1/QoS2 PUBLISH Packet Identifiers occupy the server window until the corresponding PUBACK/PUBREC bytes are actually written by the dedicated socket/TLS writer. Exceeding the window yields `DISCONNECT 0x93`.
- Server -> Client QoS1/QoS2 honors the peer's CONNECT Receive Maximum without blocking the publisher on network ACKs. Messages beyond the window remain pending in Session state.
- Pending QoS1/QoS2 carry a monotonic persisted `enqueue_order`, so mixed/offline queues do not inherit arbitrary `HashMap` iteration order and survive restart deterministically.

### Maximum Packet Size

- `PIPISTRELLE_MAX_PACKET_SIZE` defaults to `16777216` bytes and is advertised in CONNACK.
- The inbound fixed header is inspected as soon as Remaining Length is complete; oversized packets are rejected with `0x95` before the broker buffers the full body.
- Outbound MQTT Control Packets are suppressed when they exceed the peer limit. The initial CONNACK drops optional capability properties when necessary; if even its mandatory representation cannot fit, the connection is closed before Session ownership is mutated.

### CONNECT and wire correctness

- A zero-length CONNECT ClientID receives a server-generated identifier via Assigned Client Identifier and can resume a persistent Session with that value.
- CONNECT parsing is incremental across arbitrary TCP fragmentation under the existing handshake deadline.
- Receive Maximum `0`, Maximum Packet Size `0`, duplicate singleton CONNECT properties, zero Packet Identifiers, malformed/non-minimal Variable Byte Integers, malformed Topic Filters and MQTT-disallowed UTF-8 are rejected.
- `/info` exposes `unsubscribe`, `server_assigned_client_id`, `strict_mqtt_utf8`, `receive_maximum` and `maximum_packet_size`; Prometheus exports the two configured flow limits.

### Validation before release

The pre-release functional gate reached **32 Rust tests**, **23 raw MQTT v5 scenarios**, **10 destructive SIGKILL/restart scenarios**, and **6/6 integration checks**. A dedicated low-limit broker also verified that two QoS1 PUBLISH packets sent in one TCP burst with `Receive Maximum=1` produce the first PUBACK and then `DISCONNECT 0x93` for the excess flow, proving credit release happens after writer I/O rather than queue insertion.

- **50M QoS0 ingest, 3 fresh repeats:** 20.792 / 20.328 / 18.582 M msg/s; **median 20.328 M msg/s**, 0 failures. A separate exact counter gate increased Prometheus by `50,000,050` (50M publishes + 50 completion markers).

- **200k QoS1 end-to-end:** **210.97k msg/s**, 0 failures. This path now pays exact bilateral Receive Maximum accounting and remains dominated by per-message persistence; performance optimization is deferred rather than weakening flow-control semantics.

## V2 2.1.2.3 — SVE fast path + release engineering

`2.1.2.3` keeps the protocol surface of `2.1.2.2` and closes the current Topic Alias performance pass. Linux/AArch64 builds can use a runtime-detected SVE gather matcher for the stable 9-byte QoS0 alias layout; mismatches fall back to scalar localization and then the normal MQTT parser, preserving validation-before-forwarding. Non-SVE/non-AArch64 builds use the portable path.

The release also hardens two implementation details found by Clippy: alias expansion exposes initialized output length only after all bytes are written, and retained-state restore no longer carries a synchronous lock through async persistence cleanup. CI now covers formatting, Clippy, release tests and full Docker protocol/restart suites, while RustSec and CodeQL provide dependency/static security analysis.
The release also removes the unmaintained direct `rustls-pemfile` dependency flagged by RUSTSEC-2025-0134, using the maintained PEM APIs in `rustls-pki-types` instead. The final local RustSec audit is clean.

Orange Pi tuning reached **38.981 M msg/s** as the best short Topic Alias E2E run and a practical ~38–39M range. 40M sustained was not achieved and is not a release claim.

Final `2.1.2.3` release gates: **52/52 Rust**, Clippy correctness/suspicious/lock-across-await checks clean, **RustSec clean**, **6/6 integration**, **25/25 raw MQTT v5**, and **10/10 destructive SIGKILL/restart** against the exact Docker image reporting `2.1.2.3`.

## Authentication hardening

Argon2id verification is executed through Tokio `spawn_blocking` and protected by `PIPISTRELLE_MAX_AUTH_CONCURRENCY` (default `4`). Example credentials use the OWASP minimum Argon2id profile of 19 MiB, t=2, p=1 to balance password resistance with SBC memory pressure.
